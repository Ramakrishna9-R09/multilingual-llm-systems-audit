# Part A - Tokenizer audit

## A1. Evaluation corpus

The evaluation corpus is the complete **FLORES-200 devtest** split for five
line-aligned languages: English (`eng_Latn`), Hindi (`hin_Deva`), Kannada
(`kan_Knda`), Tamil (`tam_Taml`), and Telugu (`tel_Telu`). Each file has 1,012 sentences; row *i*
in every file translates the same source content. This is the crucial control:
when the denominator is a parallel sentence, the semantic payload is held
approximately constant across languages.

`scripts/prepare_flores.py` downloads the official archive or consumes a local
one, verifies the count, trims leading/trailing Unicode whitespace, writes UTF-8
NFC text, and records the archive SHA-256 in
[`data/flores200_devtest/manifest.json`](data/flores200_devtest/manifest.json).
Interior whitespace is preserved; no lowercasing, deduplication, or
language-specific filtering is applied. The source corpus consists of
professionally translated web-article sentences; the FLORES project documents
3,001 sentences from 842 articles across its splits and an average length of
about 21 words.

This corpus estimates tokenizer compression for parallel, edited prose. It
does **not** estimate our product's request mix or output quality. It lacks
chat turns, code-switching, Romanized Indic text, typos, emoji, very long
contexts, and the regional/register variation of actual users. It also cannot
show whether a tokenizer/model change preserves task quality. Production data
and model-quality evaluation remain necessary before a routing launch.

Sources: [FLORES-200 documentation](https://github.com/facebookresearch/flores/blob/main/flores200/README.md), [official archive](https://dl.fbaipublicfiles.com/nllb/flores200_dataset.tar.gz), and [XLM-R model card](https://huggingface.co/FacebookAI/xlm-roberta-base).

## A2. Script and metric audit

All evidence below is generated by `scripts/run_analysis.py` and saved in
`results/audit_variants_gpt2.csv`. The command and the raw before/after values
are also logged in [`../NOTEBOOK.md`](../NOTEBOOK.md).

### 1. Literal-space splitting is a code bug

`fertility.py` uses `line.split(" ")`. Repeated spaces create empty “words”; a
tab would not split at all. The provided samples each contain a double space,
which makes the reported denominator too large and fertility too small.

| Corpus / language | Exact intern mean | `split()` mean | Effect |
|---|---:|---:|---:|
| Provided English sample | 1.2652 | 1.2831 | +1.41% |
| Provided Hindi sample | 7.4485 | 7.5985 | +2.01% |
| FLORES Kannada | 22.4601 | 23.0255 | +2.51% |

The fix is `line.split()`, which treats runs of Unicode whitespace as one
separator. The direction is predictable: removing empty “words” decreases the
denominator, increasing tokens per word.

### 2. Lowercasing changes the workload

The script silently lowercases every line before counting. That is not a
benign way to “remove noise” for a production cost claim: a model receives the
original byte/text sequence, including names and acronyms. On FLORES English,
the intern's lowercased run uses 27,994 tokens; preserving case uses 27,044,
so lowercasing adds **950 tokens (+3.51% relative to the preserved-case
input)**. Hindi is nearly unchanged because it has no case. Thus this choice
raises the English baseline and makes the Hindi/English gap look smaller than
it is for the actual text.

### 3. Mean of line ratios is the wrong cost estimator

The code's docstring says it averages a per-line token/word ratio. A workload
cost is total tokens divided by total units of work; averaging ratios gives a
one-token sentence the same weight as a 40-token sentence. On the same,
case-preserved FLORES input, GPT-2's Hindi estimate is 7.8672 when averaged by
line but 7.8269 after aggregating tokens and words (+0.52%). For Kannada the
difference is 23.0242 vs 22.8239 (+0.88%). The empirical direction is modest
here, but it is not guaranteed and it is conceptually the wrong estimator for
the cost of serving the full corpus.

### 4. “Characters” is an ambiguous denominator, not a neutral fairness check

`len(text)` counts Unicode code points, while a person sees grapheme clusters
and a provider bills byte/token sequences. Indic vowel marks and conjuncts make
code points especially unlike visible characters. The old `tok/char` field is
therefore correctly computed *as tokens per code point*, but it cannot validate
a per-word claim or decide semantic-request cost. The corrected analysis shows
graphemes and UTF-8 bytes explicitly rather than treating any one as universal.

### Suspicious but correct: NFC normalization

The normalization line should stay. It makes canonically equivalent text count
the same instead of making the result depend on how a keyboard serialized it.
The controlled probe in `results/normalization_probe.csv` uses `café`: GPT-2
counts NFC as 3 tokens and its decomposed NFD spelling as 4 raw tokens; after
NFC, both count as 3. NFC does not make different user messages identical - it
only removes an encoding accident.

## A3. Corrected cross-language analysis

Method: count body tokens only (no BOS/EOS/other wrapper tokens), preserve
case, aggregate totals over the entire corpus, and apply the same procedure to
both tokenizers. GPT-2 is OpenAI's GPT-2 BPE encoding through `tiktoken`.
XLM-R uses the official `FacebookAI/xlm-roberta-base` SentencePiece model,
which is multilingual. Full-precision, machine-readable results are in
[`results/corrected_metrics.csv`](results/corrected_metrics.csv) and
[`results/cross_language_ratios.csv`](results/cross_language_ratios.csv).

### Headline metric: tokens per parallel sentence

| Tokenizer | English | Hindi | Kannada | Tamil | Telugu |
|---|---:|---:|---:|---:|---:|
| GPT-2 BPE | 26.72 | 198.31 (7.42×) | 363.01 (13.58×) | 415.19 (15.54×) | 346.59 (12.97×) |
| XLM-R SentencePiece | 30.30 | 37.77 (1.25×) | 40.97 (1.35×) | 40.86 (1.35×) | 39.89 (1.32×) |

For a routing-and-cost decision, **tokens per parallel sentence** is the single
number to lead with. Each numerator is the billed/computed unit and each
denominator holds the translated semantic request fixed. A whitespace word is
language-specific and unstable; a grapheme is display-oriented; UTF-8 bytes
are transport-oriented. They remain useful diagnostic metrics, but none is a
better substitute for a matched request.

### Diagnostic denominators (tokens per unit)

| Tokenizer / language | Whitespace word | Grapheme cluster | UTF-8 byte |
|---|---:|---:|---:|
| GPT-2 English | 1.235 | 0.205 | 0.205 |
| GPT-2 Hindi | 7.826 | 2.335 | 0.595 |
| GPT-2 Kannada | 22.818 | 4.065 | 0.979 |
| GPT-2 Tamil | 25.047 | 4.213 | 0.997 |
| GPT-2 Telugu | 20.708 | 4.581 | 0.992 |
| XLM-R English | 1.400 | 0.232 | 0.232 |
| XLM-R Hindi | 1.491 | 0.445 | 0.113 |
| XLM-R Kannada | 2.575 | 0.459 | 0.110 |
| XLM-R Tamil | 2.465 | 0.415 | 0.098 |
| XLM-R Telugu | 2.384 | 0.527 | 0.114 |

The denominator materially changes the apparent gap - e.g., GPT-2 Hindi is
6.34× English by whitespace word but 7.42× by matched sentence. This is why
the original report's agreement between `tok/word` and `tok/char` was not
validation; it compared two quantities that do not hold the same thing fixed.
